# Security

## Posture of a fresh deploy

| Risk on a public URL | Upstream default | This template |
|---|---|---|
| Anyone creates a profile | open sign-up | `INVITE_ONLY=1` — passkey and password sign-up need an admin-issued invite |
| No admin to issue invites | none | owner profile seeded on first boot, `admin: true` |
| Guest door | on | `ALLOW_GUEST=0` |
| Throttle sees only the proxy | — | nginx real-IP from the edge's `X-Real-IP` (client-sent values are dropped by the edge), `TRUST_PROXY=1` |
| Session cookie over HTTP | — | `ORIGIN` is https, so openGym marks the cookie `Secure` |

The owner password is generated by Railway, read from the environment once, hashed with openGym's scrypt
`hashPassword`, and never logged. openGym's own controls apply unchanged: CSRF origin checks, per-name and
per-address sign-in throttling, one-shot invite codes, per-profile data and upload isolation.

## Notes

- **API port 3000** listens on all interfaces inside the container. Railway routes the public domain to `$PORT`
  (nginx) only; 3000 is reachable solely from other services in the same Railway project, of which this template
  has none.
- **AI coach** is off until an admin enables it in Settings and adds a provider key; `COACH_DISABLED=1` forces it off.
  The image is upstream's default target (no Claude Agent SDK / Codex runtime).
- **Backups:** `/storage/data` is the whole instance (profiles, passkeys, workouts, the session signing `secret`,
  uploads). Losing `secret` signs everyone out.

Report issues with the wrapper at https://github.com/youssefsiam38/opengym-railway/issues; openGym issues upstream
(see upstream's SECURITY.md).
